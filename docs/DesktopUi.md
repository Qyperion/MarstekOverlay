# Desktop UI

`src/Desktop` shows what `StationPipeline` publishes ([Architecture.md](Architecture.md)). What the user sees is described in the [README](../README.md); this is how it is put together.

## Start-up and shell

`App.OnStartup` builds a generic host through `StartupConfiguration/AppHost` (`ContentRootPath` is the folder of the exe, so a shortcut or an autostart entry can launch it from anywhere), hands it the synchronization context of the UI thread for the station pipeline, validates the options and starts `AppShell`. Registrations are in `StartupConfiguration/ServiceCollectionExtensions`; the container validates scopes, so a window's view model cannot be taken from the root.

Before the host is built, and so before the log, `settings.json` or `history.db` are touched, `Services/SingleInstance` claims the data folder (`Storage:RootDirectory`, read from the host builder's configuration, command line included). The claim is a named auto-reset event, `Local\MarstekOverlay-` followed by the SHA-256 of the folder's full path with trailing separators trimmed and in upper case, so one folder written differently is one name and a temp folder used for a check never meets the installed copy. A start that finds the event already there sets it and exits with code 0; the copy that created it waits on it from the thread pool and answers each set with `AppShell.ShowOverlay` on the UI thread. The event is let go of in `OnExit` only after the host, and with it `history.db`, has been disposed. Until then the closing copy no longer shows its panel, so `OnExit` first creates a second named event, the claim's name followed by `-Exiting`, and sets it once the claim is let go of. A start that finds that event waits for it — at most 5 s — before it claims the folder; "Exit from the tray, then click the shortcut at once" therefore always ends with one running copy.

An exception nothing catches is logged. On the UI thread the app then shows what happened and where the log is, and closes the regular way, which takes the tray icon away and closes `history.db`; one on another thread ends the process whatever is done and `OnExit` does not run, so it is logged and shown, and the tray icon is taken out first through `Dispatcher.Invoke` with a 2 s limit — otherwise it would stay in the notification area until the mouse passes over it. `history.db` is then closed without `Dispose`, and the process ends with the code of an unhandled .NET exception (`0xE0434352`) rather than 1. An exception of a task nobody awaited is logged as an error and changes nothing.

Debug builds take two hidden keys for checking the failure paths on the running app, `--Debug:FailOn=Ui|Background|Database` and `--Debug:FailAfterSeconds=<n>` (10 by default): `Services/FailureDrill` throws on the UI thread or on a thread-pool thread, or disposes `HistoryDatabase` while the app runs. The whole class is inside `#if DEBUG`; a Release build has none of it.

`AppShell` (`IShell`) owns the windows: it applies the language before any window exists, shows the panel — unless `Overlay.IsHiddenAtStartup` leaves the window created and hidden, for the tray, a second start or a click on a notification to show — and the tray icon, starts the monitor for the saved station, and opens the settings window when no station is saved. Following the settings is `Services/SettingsFollower`, which has no windows and is tested on its own: `FollowLanguage` hands the saved language to `Localizer` now and on every change, `FollowStation` starts the monitor for the saved address, restarts it when the address changes and stops it when the address is cleared. The settings and Details windows are a fresh window and view model on every opening, one of each at a time. Each opening gets a DI scope of its own, disposed of when the window closes: the root container keeps every disposable it hands out until the app exits, and would keep every closed window with it. Asked for again while open, a window is restored if minimized and activated.

## Panel

`OverlayWindow` is a borderless, transparent window sized to its content. The card sets the width (252) and carries the scale as a `LayoutTransform`.

- **State.** `OverlayViewModel` listens to `StationPipeline.StateChanged` and calls `OverlayPresenter.Present`, which returns an immutable `OverlayState`: header, charge, rows, alerts, chart, the compact line, the tray summary. A one-second `SecondsClock` (a background-priority `DispatcherTimer`, shared with the Details window) calls it again, so durations and the forecast move between polls. The clock runs only while the panel is visible (`FollowVisibility`).
- **No needless rebuilds.** `OverlayState.KeepingListsOf` keeps the same list instance when its texts did not change, and the state is not replaced at all when nothing changed. Rebuilding rows every second would close a tooltip under the cursor.
- **Rows.** `OverlayRowKind` lists them in display order; `IsShownByDefault` separates the original five from the opt-in ones. `OverlaySettings` therefore has two lists — `HiddenRows` (default-on rows switched off) and `ShownRows` (default-off rows switched on) — so a settings file saved before a row existed keeps showing exactly what it showed. Ask and change only through `Shows(kind)` and `Show(kind, isShown)`. A row is a `Label` and a `Value`; the forecast, worded as a whole, has no label, and is a row only while the source is the battery — on mains or before the source is known it stays off the panel, while the compact line and the tray tooltip keep telling it. The Battery row is the bare `PowerSourceRule.BatteryPower`, with no mark for a calculated value. `Controls/ReadingRowPanel` puts the label at the left edge and the value at the right, and moves a value that does not fit the line under its label, where it may wrap — a grid would squeeze the summary of an outage into a narrow column. Where a reading needs both in one text, as in the tray tooltip, `Phrases.Labelled` joins them.
- **Heading buttons** — refresh, Details, settings, hide — are glyphs of the icon font of Windows (Segoe Fluent Icons, falling back to Segoe MDL2 Assets, which has the same glyphs at the same codes), so each carries its name in `AutomationProperties.Name` as well as in the tooltip.
- **Compact view** (`IsCompact`): one line — a source mark, the charge coloured by the thresholds, the BACKUP load, a brief forecast, and "⚠" in the tone of the gravest warning. No rows, chart or buttons; the chart is not even built. A double click opens the Details window; a single press still drags.
- **Stale data.** `OverlayState.StaleText` is empty while answers arrive in time, and the row collapses. After 2 min 16 s without a fresh answer (four poll cycles, `ReadingFreshness.TrustedFor`) it reads "Data from 12:55:00 is stale". That covers `ES.GetStatus`, which most rows come from; the rows of other requests — battery temperature, Wi-Fi signal, operating mode — read "no data" once their answer is older than `ReadingFreshness.TrustedFor`, the limit that marks a stale card in the Details window.
- **Placement.** `Views/PanelPlacement.Within` finds the nearest place where the whole panel is inside the virtual desktop. The window applies it on every change of its size and after a drag. Only the shown position shifts; the remembered one does not, so a panel parked at an edge returns to its place once it fits again.
- **Click-through** (`IsClickThrough`) is the extended window style `WS_EX_TRANSPARENT`. The panel's own menu is then unreachable; the mode is switched off from the tray or the settings window.
- **Menu.** `Services/PanelMenu` describes what the panel's own menu and the tray menu offer — text, action, tick, hint — in groups that a menu sets apart with separators; the tray adds showing and hiding the panel in front. The panel fills its context menu from it in code-behind each time it opens (`ContextMenuOpening`). The panel is an owned window (WPF owns a window that is not in the taskbar), so Alt+Tab does not list it.
- **Focus.** The panel has `WS_EX_NOACTIVATE`, set in `OnSourceInitialized`: a click, a button or a drag leaves the keyboard with the window the user was typing in. Windows moves such a window only once a drag ends, so `FollowDrag` moves it along on every `WM_MOVING`. Opening the context menu does activate the panel, as a menu of an inactive window gets no keys and is not closed by a click elsewhere. Windows opened from the panel activate themselves.
- **Chart height.** `LoadChartView` sets its own `MinHeight`: the charge band, the gap and a few pixels of load band; any lower and it would draw nothing.

## Tray icon

`TrayIcon` wraps a WinForms `NotifyIcon` — WPF has none — and implements both `IStatusIndicator` (the icon and its tooltip) and `INotificationChannel` (balloon tips).

- **Image.** `TrayIconImage` draws a battery filled by the charge and coloured by the same thresholds as the charge bar, a yellow triangle for running on battery, a grey outline with a red cross for no fresh data. The size is `SystemInformation.SmallIconSize`.
- **Redraw only when it would differ.** Everything the image depends on is a `TrayIconLook(Size, FilledColumns, ChargeTone, Mark)`; the charge is reduced to a number of filled columns first.
- **Handles.** `TrayIconImage` owns the handle from `Bitmap.GetHicon` and releases it with `DestroyIcon`; the icon is replaced before the previous one is released. Measured: 20,000 redraws leave the GDI count unchanged, while 200 icons made with `Icon.FromHandle` and never destroyed leak two GDI objects and one USER object each.
- **Tooltip.** `NotifyIcon.Text` takes at most 127 characters. `TrayIcon.Fit` drops the app name first, then the last lines, and only then truncates.
- **Menu.** `Services/TrayMenu`, a `ContextMenuStrip` built without the `NotifyIcon`. The items are made once from `PanelMenu` and worded and ticked anew each time the menu opens, since both the state behind them and the language may have changed; a click runs the entry of that opening. WinForms has no dark menu, so `TrayMenuRenderer` paints this one in the colours of the palette, tick included.
- **A click on a notification** calls `IShell.ShowOverlay` → `OverlayWindow.ShowOnTop`, which raises the panel above the windows covering it without taking the keyboard.

## Settings window

Four tabs — Station, Panel, Alerts, General — over `SettingsViewModel`, which holds the live switches, the typed numbers and **Save**, and exposes three parts of its own, each a scoped service of the window's scope: `Probe` (`StationProbeViewModel` — the address and the port, **Find stations**, **Test connection** and its report), `StoredData` (below) and `Status` (`StatusLine`, the one status line every part writes a finished `StatusMessage` to). What a typed field stands for, and what to say when it stands for nothing, is `Presentation/SettingsInput`, a set of pure functions with the same limits as `UserSettingsRepair`; the status texts are `Presentation/SettingsMessages`. A page is a stack of titled sections (`GroupBox`, restyled in `WindowStyles.xaml`) inside a scroll viewer, so a screen too low for the window scrolls the page instead of cutting it off; what an option does is written under it in the `Hint` style rather than hidden in a tooltip. On the Station tab the list of found stations and the report stay collapsed until there is something in them. Appearance (language, rows, opacity, scale, compact view, chart) is tried out live through `UserSettingsStore.Change(..., persist: false)` and written once when the window closes; the station address and the numbers are applied by **Save** after validation. The window follows changes made from the menus while it is open.

**Wrong values.** The fields that only Save applies are checked when it is pressed — the station fields also by **Find stations** and **Test connection** — and all of them at once, so every wrong one is marked together. A number takes a decimal point or comma and must be finite (`double.TryParse` reads "NaN", which no range check turns down); the charge thresholds are therefore apart by spaces or semicolons, with a comma right after a number still ending it. The address is four decimal numbers as `IPAddress` writes them back (`StationEndpoint.TryParseAddress`): `IPAddress.TryParse` alone reads "192.168.1" as 192.168.0.1 and "050" as octal 40. `SettingsViewModel` and `StationProbeViewModel` each keep the messages of their own fields in `FieldErrors`, by the name of the bound property, and hand them to WPF as `INotifyDataErrorInfo`: that is what turns the frame of a text box red (the `Validation.HasError` trigger of the text box template in `WindowStyles.xaml`; the stock adorner is switched off, since a tab switched away and back loses it), while the text under the field is bound to `Errors[Property]`. A field stops being marked as soon as it is edited and is checked again by the next attempt. `SelectedTabIndex` moves to the first tab with a marked field unless the open one has one. A saved address or port that stands for no station — a file edited by hand — is marked from the moment the window opens, and again in a new language, for as long as the field holds what was saved. A row of a page with a label, a field, its message and a hint is `Controls/FieldRow`, a grid built in code: a templated one would keep its texts from UI Automation, and the field inside stays bound to the view model, so that its own validation turns its frame red. Under **No answer for longer than** `SettingsInput.StaleAfterInEffect` tells the limit in effect when the poll makes it longer than the one typed (`SilenceLimit`).

**Unsaved edits.** Closing drops the address and the numbers that were typed and not saved. `MayClose`, asked by the window's `Closing`, refuses the first attempt after such an edit and says so in the status line; the second one closes, unless another message has taken the warning's place in the meantime. A search and a connection test disable each other's button while they run, so their messages do not interleave; a search the transport fails is reported on the status line.

**Deleting stored data** is the last section of the General tab and a view model of its own, `StoredDataViewModel`, which `SettingsViewModel` exposes as `StoredData`: three ticks (samples, outage journal, log), the period to keep and a button that is enabled once something is ticked. It is an action, not a setting — nothing of it is saved. The period offered first is the longest, which deletes least. The window asks first with a message box whose default answer is "No" and which names what is ticked and what is kept (`StoredDataPresenter.AskToDelete`) (as with the save dialog of the export, the question is in the window and the deleting in the view model); how it went is written under the button. The samples and the journal are deleted on the UI thread; the log, up to three files of 5 MB read and rewritten, on the thread pool, with the button off until it is done. Meanwhile `DiagnosticLog` holds back what is logged instead of keeping the writer, the UI thread among them, waiting on its lock, and writes it to the reopened file afterwards. The mechanics are in [HistoryAndCharts.md](HistoryAndCharts.md).

**Autostart** is not a setting in the file. `Services/Autostart` writes the value `MarstekOverlay` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, and the checkbox shows what the registry holds: a copy in the file could disagree with what Windows will actually do, and "repairing" the entry at start-up would repoint it at `bin\Debug` every time the app is run from the repository. Task Manager disables an entry without touching `Run`: it writes a value of the same name under `…\Explorer\StartupApproved\Run` whose first byte is odd (3, against 2 for enabled). The checkbox reads that too, and every change of the checkbox deletes that value, so a ticked box always means an entry that will run. A write that fails is reported on the status line and the box goes back to what the registry holds. The view model sees it through `IAutostart`. The entry is the quoted path of the exe and nothing else, so command-line arguments do not reach a copy started at sign-in. A copy whose folder was moved finds the entry naming the old place and shows the box unticked until it is ticked again; `tools/Publish/Publish-App.ps1` writes the same entry, in the same form, on every install.

The **version** at the bottom of the window is the assembly version of the exe, `Version` in `Desktop.csproj`, in three numbers.

## Details window

`DetailsWindow` with `DetailsViewModel`, three tabs. `DetailsViewModel` holds the cards, the one-second clock and the subscriptions to the pipeline and the language, and hands every tick, change of state, deletion and switch of language to the view models of the other two tabs: `Journal` (`JournalViewModel`) and `Charts` (`HistoryChartsViewModel`).

- **Station.** `StationSections.Describe(snapshot, source)` describes every value once, for both the cards and the **Test connection** report. Cards and their rows are long-lived objects updated in place, so tooltips stay open and UI Automation keeps reading them. A card whose method stopped answering is marked stale (`StationCardViewModel.IsStale`, from `ReadingFreshness.TrustedFor`: four fast poll cycles — the interval plus the poll's own requests a pause apart — or three slow intervals, each up to a fast cycle late).
  - **Groups.** `DetailsViewModel.CardGroups` lays the cards out in three titled groups, each a row of cards as tall as its tallest: power (energy system, battery, operating mode), device and connection (device, Wi-Fi, Bluetooth), accessories (energy meter, solar inputs). The report keeps the order of the requests.
  - **What is not there is not listed.** A section has a `Note` in place of rows when the request brought no values: no answer, not supported (`UnsupportedMethods`), or — `SectionState.NotConnected`, from `PolledMethod.IsDisconnected` — an answer saying nothing is connected, which for the meter reads "CT not connected" instead of seven zeros. Such a section still tells when the station said so, and never turns stale: its request is not sent again ([MarstekLocalApi.md](MarstekLocalApi.md), "Polling"). Following the same rule, the energy system leaves out solar power and total solar energy on a station that refuses `PV.GetStatus`, unless one of them is not zero, and the operating mode leaves out its copy of a meter without a CT.
  - **Check again**, in the room of the third card of the accessories, calls `StationMonitor.CheckAbandoned`; the ages of the two cards show that the station was asked.
  - **Each value once.** Where several answers bring the same value, it is told with the answer that reads it most often or that it belongs to, and the others leave it out. The operating mode leaves its grid power, backup output power and charge to the energy system, and the battery its charge, each for as long as the energy system has that value. The energy system leaves its capacity to the battery when the battery tells the same rated capacity. The device leaves out a MAC, a network name or an address that the Wi-Fi or Bluetooth answer tells the same (compared without regard to case); a reported IP that differs from the one Wi-Fi tells keeps its row, as it can stay at a previous DHCP address for hours. With one answer missing the other keeps its rows, so nothing is lost. The cards fill in over the first seconds after a start, and rows of the device and of the energy system drop out as the later answers arrive.
  - **Counters at zero.** The four energy totals of the energy system are left out while they read exactly zero: Venus E 3.0 keeps the load total at zero with the load on the backup output. A total the answer came without still has its row, with a dash.
  - **Wording.** Battery power is `PowerSourceRule.BatteryPower` told by its direction and without a sign — "charging 2200 W", "discharging 286 W", plain "0 W" under half a watt (`Phrases.BatteryPower`, shared with the line above the charts) — and with no mark for a value worked out from the other flows. Only while the source is not known and the value holds on the battery alone — the report of a connection test, the first answers after a start — does it say so in brackets. The panel's Battery row keeps the signed number. The Wi-Fi signal is followed by a word for it: excellent from −50 dBm, good from −60, fair from −70, weak below. The Bluetooth states seen so far, `connect` and `disconnect`, are worded; any other is passed through as it came.
- **Outages.** Calendar totals and one calendar month of the journal at a time ([PowerSourceAndOutages.md](PowerSourceAndOutages.md)). An outage that crosses a month boundary is listed whole in both months; a date of another year than the month's names its year. Under the list of a past month is its total (`DetailsPresenter.DescribeMonthTotal`), which counts only the part inside the month; the current month has none, as the "this month" card already tells it.
- **Export.** `Presentation/JournalExport` composes the CSV as a pure function. The file is meant for Excel: columns separated by the regional list separator, dates in the regional short format with `HH:mm:ss`, durations as `h:mm:ss` with hours not folded into days, an outage that crosses a bound of the month cut at it with its share of the energy (`OutagePart`) and marked in the last column, its charge and "not seen" marks left empty at the cut side, UTF-8 with a byte order mark (without it Excel garbles Cyrillic), and no `sep=` line (with it Excel ignores the byte order mark). The columns are start, end (or the word for ongoing), duration, energy in Wh, charge at the start and at the end in %, start not seen and end not seen ("yes" or empty), and the cut; the titles follow the language of the app, the values the regional format. A file in this form opens in Excel with a double click, its columns split and its dates and durations read as values. The suggested name is `marstek-outages-<yyyy>-<MM>.csv`. The save dialog is in the window, the writing in the view model.
- **Charts.** Three charts over 1 hour to 7 days ([HistoryAndCharts.md](HistoryAndCharts.md)). The samples of the period are kept by `Monitoring/History/TrailingSamples`: read once, then followed. The legend under them is drawn with the brushes the charts themselves take, so a colour changed in the palette changes in both.
- **Place.** `UserSettings.Details.Window` remembers size, position and the maximized flag. `Views/WindowPlacement.Within(workAreas, wanted, smallest)` keeps a saved place only if the monitors' work areas show it whole; otherwise the window moves to the monitor showing most of it. Work areas come from `System.Windows.Forms.Screen`, converted from pixels with the transform of the window's `HwndSource` — in `OnSourceInitialized` the window is not yet the content of its handle, and `PresentationSource.FromVisual` returns null.
- **Dark title bar** in both ordinary windows: `WindowExtensions.UseDarkTitleBar` sets DWM attribute 20, or 19 on Windows 10 before 2004.

## Localization

Texts are in `Localization/Strings.resx` (English) and `Strings.uk.resx` (Ukrainian); the class `Strings` is generated at build time. Code reads `Strings.Key`. XAML uses `{loc:Text Key}`, a binding to the indexer of `Localizer`, which is what lets open windows follow a switch of language. `AppLanguages` lists the languages; without a saved choice the app speaks English, whatever the display language of Windows. Why a file or the registry was left as it was — the autostart entry, clearing the log, the export — is worded by `Presentation/FailureReasons` from the kind of the exception (no access, a file in use or out of reach, anything else); the message of the exception is in the language of Windows and goes to the log only.

Units are translated too (`Presentation/Units`), while digits follow the regional format of Windows, a setting of its own. Shared wordings of durations and moments are in `Presentation/Phrases`, and a text with placeholders is filled in through `Phrases.Format` only, in the regional format. A forecast's time keeps its hours even when there are none ("≈ 0 h 40 min"), unlike a duration. The name of the product is the text `Common_ProductName`, for the panel's title, the tray tooltip, message boxes and notifications alike.

A new language is a `Strings.<code>.resx` and an entry in `AppLanguages.All`. `tests/DesktopTests` checks that every translation has the same keys and the same placeholders as the English texts.

## Styling

`Styling/Palette.xaml` holds every colour. `Presentation/Tone` names the semantic ones (primary, secondary, positive, info, warning, critical); a presenter picks a tone, and `ToneToBrushConverter` or `TonePalette` turns it into a brush. `Styling/WindowStyles.xaml` carries the shared dark styles of the two ordinary windows, with templates of their own for every control whose stock look is light: button, tab, check box, radio button, slider, scroll bar. It also has the shared pieces of the two windows: `ChoiceList` (a row of radio buttons over `ChoiceOption<T>`, grouped by the `Tag` of the list), `SwitchGrid` (check boxes in two columns over `SwitchOption<T>`), `ScrollingPage`, `FieldError` and `StatusText` (a finished `StatusMessage`, red when it is an error). `Styling/CommonStyles.xaml`, merged at the level of the application because the panel does not take `WindowStyles.xaml`, has `HiddenWhileEmpty` and the brushes of the charts as implicit styles of `LoadChartView` and `HistoryChartView`. The heading and the rows of the journal are laid out by `Controls/JournalGrid`, so their columns cannot drift apart. `Styling/MenuStyles.xaml` does the same as `WindowStyles.xaml` for context menus and is merged at the level of the application, so it reaches the panel's menu and the ones text boxes bring along; its menu item has no part for a submenu. Code that paints outside WPF takes the colours of surfaces from `Styling/SurfacePalette`. P/Invoke declarations are in `Interop/NativeMethods`.

The **application icon** is `Assets/App.ico`, named by `ApplicationIcon` in `Desktop.csproj`; the ordinary windows, the taskbar and Explorer take it from the exe. It is drawn by `tools/AppIcon/New-AppIcon.ps1` — a battery on a tile, in the proportions of the tray icon and the colours of the palette, each of the eight sizes on its own pixel grid — so a change of the icon is a change of that script and a rerun. The tray icon stays the one drawn at run time.
